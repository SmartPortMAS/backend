# 현재 시스템 상태 vs 이번 대화 결정 — 갭 분석

대조 기준: 팀 공유 "멀티 에이전트 하역 관제 시스템 사용 시나리오"(2026-07-19 실측) vs 이번 대화의 결정(온산 2클러스터, R1~R14 안전규칙, cargo 매핑, 인화성 방지 선석배정)

전제: 대상 선석을 온산항 처용리+산암리 2클러스터로 좁힌 것은 이번 대화의 확정 변경사항이다. 아래에서 현재 문서의 "5개 파일럿 선석군"으로 되돌리자는 얘기는 하지 않는다. 그 변경이 시스템에 어떤 파급을 주는지, 그리고 대화에서 정한 것 중 아직 시스템에 없는 것을 짚는다.

---

## 0. 먼저 정정할 사실 두 가지

### cargo_cas_map은 새로 만들 게 아니라 이미 있다

입항정보 PDF 2종을 전수 검색한 결과 UN번호 0건, 취급화물 표기는 "케미칼/기름" 카테고리뿐이다. PDF로는 화물 목록을 만들 수 없다. 그런데 현재 시스템에 이미 Neo4j `Chemical` 34종이 `cargo_category`, `imdg_class` 속성까지 붙어 존재한다. 계획서의 14종이 34종으로 확장된 것이고, 내가 만들자던 화물명↔CAS↔IMDG 매핑은 사실상 이 노드셋이다. 별도 시드 파일은 불필요하다.

### 진짜 병목은 "화물 마스터"가 아니라 "선석에 실제로 뭐가 있나"의 바인딩

34종 마스터는 있지만, 특정 선석에 지금 무슨 화물이 있는지를 실데이터로 채우지 못한다(문서 6-1①). 이게 안전 차별점의 실질 병목이다. 아래 GAP 2에서 다룬다.

### 팀이 이미 만든 시드 두 개 (프로젝트 폴더에서 확인)

- `cargo_cas_map.csv` (15종): cargo_name, cas_no, un_no, imdg_class, flashpoint_c_ref, cargo_category까지. 특히 flashpoint 컬럼이 있어 R13 인화성 규칙 입력이 이미 준비됐다. 벤젠 행에 "정일9.18/OTK9.17 벤젠함유화물 특별취급"까지 달려 있다. PDF 9.18 원문 확인 결과 벤젠 5% 초과 화물은 이전 화물 벤젠 프리(0ppm) 증명이 필요하다 = 게이트 규칙 R15 후보.
- `berth_weather_thresholds.csv`: 터미널별 중단/이안/호스분리 풍속, 파고. PDF 9.8과 정확히 일치한다. 아래 GAP 6에서 이게 왜 중요한지 다룬다.

## GAP 1 — 온산 스코프 변경은 "좁히기"가 아니라 "인접그래프 재구축"을 요구한다 (최우선)

현재 `ADJACENT_TO` 14건은 5개 파일럿 선석군(정일1·2, OTK1·2, 현대오일신항1·2, SK5~8, 북신항에너지↔신항북방파제에너지)에만 걸려 있다(문서 6-1②).

이걸 온산 2클러스터 스코프에 대보면:
- 살아남는 것: 정일1·2, OTK1·2 (둘 다 온산). 나머지 3군(현대오일=신항, SK=본항, 북신항=신항)은 스코프 밖으로 이탈.
- 새로 필요한 것: UTK, 대한유화, 효성, S-Oil1·2, 석유공사부이, 유성, 온산1~4. 이들은 인접 엣지가 아예 없고, 문서 6-1②대로 다수가 좌표 결측(`MISSING_COORDINATE`)이다.

즉 스코프를 온산으로 옮기면 인접그래프를 처용리 안, 산암리 안에서 새로 깔아야 한다. 그리고 하나 더, 스케줄링 후보풀을 MVP 선석셋으로 제한해야 한다. 현재는 후보를 전체 69선석에서 뽑아 신항의 깊은 선석(벤젠 예시의 신항남방파제 T/S부두 등)을 1순위로 낸다. 스코프 밖 선석이 계속 추천되면 데모가 어긋난다.

이번 대화의 기여로 막힌 곳이 일부 풀린다. PDF에서 OTK(35.45661, 129.35119)와 정일(35.43778, 129.36694) 정확 좌표를 확보했다. 2개 앵커 터미널은 즉시 채울 수 있고, 나머지는 getGisHrbr로 확보한다. 인접은 수역 소속이 아니라 좌표 거리로 계산한다(온산항_MVP범위 문서 1.3).

효과: 벤젠 예시에서 1순위 선석의 `adjacent_cargos`가 빈 배열이라 안전관제가 이웃을 못 봤다. 온산 스코프 + 인접 재구축이 되면 정일/OTK에 실제 이웃이 생겨 혼재/격리 차별점이 비로소 발화한다. 스코프 변경이 곧 데모를 살리는 조건이다.

## GAP 2 — 인접화물 근사(6-1①)가 차별점의 실질 병목, PDF로는 못 푼다

현재는 인접 선석 화물을 카테고리별 대표 1종으로 채운다(액체화학→벤젠 식). 실제 화물이 아니다. 실화물 상세는 getIntgCagInfo가 키 지정형이라 벌크 수집이 안 되고, `upa_cargo_manifest` 테이블 자체가 없다.

PDF는 이 문제를 못 푼다(위 0번). 현실적 경로는 셋이다.
1. getUnloadRcd 품명 확인 (여전히 유효한 미결 작업). `upa_unload_record` 505건이 이미 있으니 컬럼에 품명/품목이 있는지부터 본다. 있으면 근사 대신 부분 실화물로 대체.
2. 위험물 신고 dg_un_no 연계 (연계키로 이미 합의됨).
3. 인접 선석 작업 시나리오 시뮬 데이터셋 구축 (계획서 명시, 문서 6-6은 미구축). 34종 마스터로 처용리/산암리 선석에 대해 만들고, 시뮬레이션임을 명확히 표시.

MVP 관점에선 3번이 가장 빠르다. 이게 6-1① 우회이자 아래 인화성 데모의 전제다.

## GAP 3 — 인화성 방지(R13/R14): 이미 있는 IMDG 이격거리를 재사용하라 (내 시드 정정)

내가 앞서 "이격거리 임계값은 ISGOTT/위험물규정에서 확보"라고 했는데, 현재 시스템이 이미 IMDG 격리코드 1~4를 물리거리 3/6/12/24m로 매핑해 쓰고 있다(문서 6-2③). 그러니 R13의 이격거리는 새로 정할 게 아니라 이 IMDG 격리거리를 그대로 쓰면 된다. 출처도 IMDG Code Ch 7.2로 이미 확보돼 있다.

R13/R14가 현재 `imdg_conflicts`보다 새로 더하는 것은 명확하다. 현재 `imdg_conflicts`는 실제 거리, 시간과 무관한 정적 Class 쌍 검사다. R13은 여기에 실제 좌표거리 대비 요구 격리거리 충족 여부, 동시 작업 타이밍, 저인화점+기상(낙뢰/고온)을 더해 공간적·시간적으로 인지화한다. 즉 정적 격리표를 상황 인지형으로 끌어올리는 게 이번 대화의 인화성 방지 기여다.

## GAP 4 — 결정론 게이트 R1~R11 상당수가 아직 시스템에 없다

현재 결정론 판정은 기상(룰엔진), 수심/점유(스케줄링), 혼재금지/IMDG(안전관제)에 한정된다. 입항정보 PDF에서 뽑은 아래 게이트는 아직 없다. 전부 LLM 없이 돌고, 실제 터미널 규정이 출처라 방어력이 높다.

- R1/R2 유조선 SIRE, 케미칼/LPG선 CDI 검사이력 없으면 접안 불가 (하드 블록)
- R3 흘수 여유, R5 전장 min/max (OTK 최소 60m)
- R6 흘수 9m 미만 & 20,000GT 미만 24시간, 이상 주간만
- R7 150,000GT 이상 UPA 사전승인, R8 도선 의무, R9 ETA 미보고, R10 Ship/Shore 점검표 2시간, R11 정박지 톤수

우선순위: R1/R2(하드 블록) + R3/R6(물리·시간)을 MVP에 먼저. 각 규칙 하나가 Cypher 쿼리 하나 = 위험 유형 하나라, 넣을수록 "조금의 위험이라도 탐지"의 재현율이 올라간다.

## GAP 5 — risk_level 비결정성이 "결정론 탐지" 원칙과 충돌한다 (6-2③)

이번 대화에서 정한 원칙은 탐지는 결정론, LLM은 설명만이다. 현재 `rule_engine_floor`는 결정론으로 재현되지만, 최종 `risk_level`은 LLM이 하한 위에서 자유 판단해 같은 입력에도 위험/배정불가가 갈린다(문서 상단, 6-2③). 안전 데모에서 심사위원이 동일 입력에 다른 판정을 보면 신뢰를 잃는다.

권고: 최종 risk_level을 (rule_engine_floor, IMDG 격리코드, 인화성 등급, 게이트 히트)의 결정론 함수로 확정하고, LLM은 checklist/reasoning/summary 문장만 쓰게 한다. 작은 변경이지만 데모 방어력이 크게 오르고, 우리가 합의한 원칙과 정렬된다.

## GAP 6 — 기상 임계값이 터미널별로 다른데 에이전트는 단일 전역값을 쓴다 (승격)

이게 이번에 드러난 가장 실질적인 갭이다. 팀의 berth_weather_thresholds.csv와 PDF 9.8 원문이 보여주는 실제 기준은 이렇다.

| 터미널 | 하역 중단 | 부두 이안 | 호스분리 | 파고(중단) |
|---|---|---|---|---|
| 정일1/2 | 풍속 17 m/s | 19 m/s | 21 m/s | 1 m |
| OTK1/2 | 풍속 14 m/s | 18 m/s | 21 m/s | 2 m |
| 현재 에이전트(계획서) | 14 m/s | - | - | 1.5 m |

세 가지가 어긋난다.
1. 터미널마다 값이 다르다. 정일 중단 풍속은 17이고 OTK는 14다. 현재 에이전트는 둘 다 14로 본다.
2. 파고가 정일은 1m로 계획서 1.5m보다 엄격하다. 현재 에이전트를 정일에 그대로 쓰면 실제로 중단해야 할 상황을 가능으로 오판한다.
3. 실제 기준은 중단 → 이안 → 호스분리 3단계 에스컬레이션인데, 현재 에이전트는 가능/불가 단일 임계다. 관제사가 실제로 필요한 건 "지금 중단인지, 이안까지 가야 하는지, 호스를 분리해야 하는지"의 단계 판정이다.

권고: 기상 에이전트를 선석별 임계 테이블 기반으로 바꾼다. 데이터는 이미 berth_weather_thresholds.csv로 있으니 배선만 하면 된다. 판정 출력도 3단계 에스컬레이션으로 확장한다. 이건 데이터가 준비돼 있어 즉시 가능하고, "조금의 위험이라도 탐지 + 관제사 관점"에 정확히 부합해 우선순위를 올린다.

추가로 커버리지 공백(6-3): 현재 기상은 울산항 격자 1개(nx=102, ny=84), 단일 관측소만 본다. 온산항은 별도 격자, 인근 관측소/부이가 필요하다. visibility 단위 버그와 조건부가능 경계 임의값도 온산 지점 붙일 때 같이 정리한다.

## GAP 7 — Human in the Loop 승인 기록이 곧 "관제사 관점" (6-4)

이번 대화의 방향은 관제사 입장에서 안전관제를 강화하는 것이다. 계획서도 관제사 최종 승인 후 하역 개시를 명시한다. 그런데 현재 API는 자동 판단만 반환하고 관제사가 승인/반려했는지, 언제 했는지 기록이 없다.

권고: 관제사 승인/반려 엔드포인트와 감사 로그(누가, 언제, 어떤 판정, 오버라이드 사유)를 추가한다. 이건 관제사 관점 그 자체이고, 시간이 쌓이면 문서 6-6이 지적한 실무 검증 데이터셋(정확도 측정용)의 원천이 된다.

## GAP 8 — 시뮬 데이터셋이 우리가 설계한 데모의 전제다 (6-6)

인접 선석 작업 시나리오 시뮬 데이터셋은 R13 인화성 데모의 전제이자 GAP 2의 우회책인데 아직 미구축이다. 처용리/산암리 선석에 대해 34종 마스터로 먼저 만든다. 탱크 저장, 하역 로그 시뮬은 그다음.

## 정렬 확인 — 이미 잘 가고 있는 것 (되돌릴 필요 없음)

- `rule_engine_floor`(결정론) + LLM 설명 분리 구조는 우리가 합의한 원칙과 이미 같은 방향이다. GAP 5는 이 구조를 최종 등급까지 밀어붙이자는 것뿐이다.
- `imdg_conflicts`가 MSDS 텍스트(`conflicts`)로는 안 걸리는 조합(에틸렌 Class 2.1 + 벤젠 Class 3)을 잡아낸 예시는, 우리가 말한 "그래프가 텍스트 검색이 놓치는 관계 위험을 잡는다"의 정확한 실증이다. 이게 차별점의 핵심이니 밀고 가면 된다.
- 오케스트레이터의 기상 우선 단락(불가면 즉시 중단) + 교차검증 + 배정불가 시 재탐색은 멀티 에이전트 교차검증 설계와 일치한다.
- 기상 `is_stale` → 판단불가 fail-safe는 정직한 엔지니어링이다. 자동수집이 멈추면 시스템이 스스로를 못 믿게 한 것은 오히려 강점으로 발표할 만하다.
- 문서 6장의 한계 자기고백 자체가 멘토링 보고서에서 신뢰를 준다. 숨기지 말고 로드맵으로 제시.

## MVP 관점 우선순위 정리

1. 온산 선석 좌표 확보(getGisHrbr, OTK/정일은 PDF값 즉시) + `ADJACENT_TO` 처용리/산암리 재구축 + 스케줄링 후보풀을 MVP 선석셋으로 제한 (GAP 1). 차별점이 실제로 발화하는 최소조건.
2. 선석별 기상 임계 + 3단계 에스컬레이션 배선 (GAP 6). berth_weather_thresholds.csv가 이미 있어 즉시 가능, 관제사 관점 고가치.
3. 인접 선석 작업 시뮬 데이터셋(34 마스터 기반) (GAP 2, 8). 6-1① 우회, 인화성 데모 전제.
4. risk_level 결정론화 (GAP 5). 데모 신뢰성.
5. 결정론 게이트 R1/R2/R3/R6 + R15(벤젠 5% 특별취급) 추가 (GAP 4). cargo_cas_map.csv의 flashpoint로 R13도 즉시. 탐지 폭 확대.
6. 온산 기상 격자/관측소, 관제사 승인 기록 (GAP 6 커버리지, GAP 7).

병행 확인: getUnloadRcd 품명 컬럼 유무(GAP 2), msds_chemical 35 vs Chemical 34 불일치 원인(6-5).
